# Content Collection Locales — Design

## Motivation

Sub-project 1 of 2 for adding a bilingual (NL/EN) blog to the marketing site
(sub-project 2: [marketing blog](2026-09-28-marketing-blog-design.md)). The
blog needs a separate NL and EN page per post, and those pages need to know
which entries belong together as translations.

Today `@waldjs/content` only reads `.md` files directly inside
`content/<collection>/` — no subdirectories, no notion of language. Rather
than working around that in the marketing site (two unrelated collections
`blog` and `blog-en`, paired by filename in ad-hoc site code), we add
first-class locale support to the framework, so every WaldJS user gets it and
the marketing site dogfoods it.

This deliberately stops short of i18n **routing** (roadmap Phase 5c): no
locale config in `wald.config.ts`, no locale-prefixed routes generated by the
router. Pages keep choosing their own routes (e.g. `src/pages/en/blog/…`).
This design is the content-layer half that 5c can later build on.

## Directory convention

```
content/blog/nl/hello.md
content/blog/en/hello.md
content/changelog/seed.md        ← unchanged: no locale
```

- A subdirectory of a collection whose name matches
  `^[a-z]{2}(-[A-Z]{2})?$` (`nl`, `en`, `en-GB`) is a **locale directory**.
  Its `.md` files are entries with `locale` set to the directory name.
- `.md` files directly in the collection directory are entries without a
  locale — exactly today's behaviour.
- Any other subdirectory is ignored, as today. No existing project changes
  behaviour: **not a breaking change.**
- A collection "has locales" when it contains at least one locale directory.

## Entry type

```ts
export type Entry = {
  slug: string       // file name without .md; identical across translations
  locale?: string    // locale directory name, or undefined
  data: Record<string, unknown>
  body: string
}
```

## API

`@waldjs/content` (Node-side, takes `contentDir`):

```ts
readCollection(name, contentDir, options?: { locale?: string }): Promise<Entry[]>
readEntry(collection, slug, contentDir, options?: { locale?: string }): Promise<Entry>
readTranslations(collection, slug, contentDir): Promise<Record<string, Entry>>
```

`wald:content` (virtual module, as today binds `contentDir`):

```ts
getCollection('blog')                        // every entry, every locale (+ unlocalized)
getCollection('blog', { locale: 'en' })      // only entries in content/blog/en/
getEntry('blog', 'hello', { locale: 'en' })  // content/blog/en/hello.md
getTranslations('blog', 'hello')             // { nl: Entry, en: Entry } — only locales that exist
```

Semantics:

- `readCollection` with `locale` returns only that locale's entries; with a
  locale that has no directory it returns `[]` (a collection may simply have
  no posts in a language yet).
- `readEntry` **without** `locale` on a collection that has locales, and no
  top-level `<slug>.md`, throws:
  `Collection "blog" has locales (en, nl) — pass { locale } to getEntry("blog", "hello")`.
  It never silently picks a language.
- `readEntry` for a missing entry throws a readable error naming the
  collection, slug, requested locale and the available locales, instead of
  surfacing a raw `ENOENT`.
- `readTranslations` returns an object keyed by locale containing each locale
  directory's `<slug>.md` that exists; `{}` if none. Unlocalized entries are
  not included.
- Entry ordering from `readCollection` stays deterministic: locale
  directories sorted by name, files sorted by name within each; unlocalized
  entries first.

## Files touched

- `packages/content/src/index.ts` — locale discovery, options, errors,
  `readTranslations`.
- `packages/cli/src/vite-plugin.ts` — virtual `wald:content` module forwards
  the options argument and exports `getTranslations`.
- `packages/cli/src/checker.ts` — `CONTENT_SHIM` gets the `locale` field, the
  options parameters and `getTranslations`, so `wald check` type-checks the
  new calls.
- `README.md` — "Content collections" section gains a locales example.
- `.changeset/*.md` — minor bump for `@waldjs/content` and `@waldjs/cli`.

## Testing

- `packages/content/src/index.test.ts`, with fixture directories:
  - unlocalized collection behaves exactly as before (regression);
  - localized collection: all entries, per-locale filtering, unknown locale
    → `[]`;
  - mixed collection (top-level files + locale dirs);
  - non-locale subdirectory ignored;
  - `readEntry` with locale; missing-locale error message; missing-entry
    error message;
  - `readTranslations`: both, one, none.
- `packages/cli/src/vite-plugin.test.ts` — the virtual module exports
  `getTranslations` and passes options through.
- `packages/cli/src/checker.test.ts` — a `.wald` file using
  `getCollection('blog', { locale: 'en' })` and `getTranslations` passes
  `wald check`.

## Out of scope

- Locale config / default locale in `wald.config.ts`, locale-prefixed
  routing, fallback-to-default-language (all Phase 5c).
- Frontmatter schemas/typed `data` (#77).
- Nested non-locale subdirectories in collections.
